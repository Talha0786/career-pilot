# 051 — Mapping/filling orchestration + document-attachment gate

**Status:** TODO | **Milestone:** M6

## Objective
Wire 048/049/050 into the actual `ApplyTask` state machine (045): `draft → mapping → filling → awaiting_review`. Fill the detected fields in a real (fresh, per-task) browser context, upload the correct tailored document, and enforce the M5→M6 boundary: a `DocumentVersion` with `needsHumanReview: true` (i.e. `isExportable() === false`, per M5 task 040) must be architecturally unusable as an attachment here.

## Files affected
- `packages/application/src/apply/commands/start-apply-task.ts` (new) — creates the `ApplyTask` in `draft`, requires an `applicationId` + a `documentVersionId`; **must check `DocumentVersion.isExportable()` before allowing `draft → mapping`** — reject/block with a typed error if the chosen document version failed claim verification.
- `packages/application/src/apply/commands/run-mapping.ts` (new) — `draft → mapping`: detect ATS (048), fall through heuristics (049) then LLM (050), persist the resulting field map as an `apply_task_steps` row.
- `apps/browser-runner/src/fill-runner.ts` (new) — `mapping → filling`: actually drives Playwright to fill the mapped fields and upload the document (via the document-store, following whatever pattern `packages/infrastructure` already uses for `DocumentVersion.renderedPdfKey` retrieval — check task 024's doc-engine output). Uploads restricted to document-store files referenced by the task (per §6 security posture) — no arbitrary file paths.
- `apps/browser-runner/src/fill-runner.ts` also handles timeouts from the design doc: mapping 90s, filling 120s.
- On completion, `filling → awaiting_review`, minting the review data (field-value diff) task 052's UI reads.

## Dependencies
- 045 (ApplyTask state machine), 048, 049, 050 (mapping pipeline stages), M5 task 040 (`DocumentVersion.needsHumanReview`/`isExportable`).

## Acceptance criteria
- A `DocumentVersion` that failed claim verification cannot reach `filling` — test this explicitly (attempt to start an ApplyTask against a `needsHumanReview: true` version, assert rejection), since this is the one place M6 could silently reintroduce the hallucination risk M5's task 040 was built to close.
- Mapping/filling timeouts are enforced (task transitions to `failed` on timeout, not left hanging).
- Every field fill produces an `apply_task_steps` row with a redacted payload (no raw sensitive values logged in plaintext, per §6).

## Test plan
- Unit: document-exportability gate rejection (fake repo returning a non-exportable version).
- Integration/Playwright: real mock-ATS-shaped fixture form (can reuse 048's fixtures ahead of 054's dedicated mock-ATS app), full mapping→filling→awaiting_review round trip, timeout-triggers-failed path.

## Status

**Architectural resolution (the same boundary story as 048/050, applied here too):**
`packages/application/src/apply/commands/run-mapping.ts` orchestrates the pipeline WITHOUT
depending on Playwright: it takes a `FieldDetectionPort` (048's known-ATS detect + 049's
heuristics, run against a live page) and this task's own `mapFieldsWithLlm` (050, in-process, same
layer) for the LLM stage. `apps/browser-runner/src/field-detection.adapter.ts`
(`PlaywrightFieldDetectionAdapter`) is the real port implementation — the one place Playwright and
application-layer orchestration actually meet, and it lives in the app (correct dependency
direction), not the package.

**State-machine bug found and fixed by this task's own tests (not left in):** the original
`run-mapping.ts` tried to enter `'mapping'` only AFTER a successful detection+LLM pass, meaning a
detection timeout or LLM error attempted `task.transitionTo('failed', ...)` while the task was
STILL in `'draft'` — illegal per 045's table (`draft` has no `failed` edge), so the transition
silently failed and the task was left stuck in `draft`, not `failed`. Fixed by entering `'mapping'`
FIRST, unconditionally, persisted immediately (crash-safety: a process death right after this save
still reads back as `'mapping'`, a retryable state), THEN attempting detection/LLM — failures now
legally transition `mapping → failed`. Caught by `run-mapping.test.ts`'s own failure-path
assertions, not found later.

**Timeouts:** the design doc's 90s mapping timeout is real (`withTimeout` wraps the
`FieldDetectionPort` call) and INJECTABLE (`mappingTimeoutMs` override) specifically so a test can
trigger it for real without waiting 90 real seconds — a 30ms-override test proves both "completes
normally under the timeout" and "genuinely transitions to `failed` when exceeded," not just
documented behavior.

**Files:** `packages/application/src/apply/commands/{start-apply-task.ts,run-mapping.ts}`,
`packages/application/src/ports/field-detection.port.ts`. `apps/browser-runner/src/{context-manager.ts,
field-detection.adapter.ts,fill-runner.ts}`. `fill-runner.ts` fills text/select/radio fields by
`TAXONOMY[key].inputType` (a real bug fixed here too: `page.fill()` doesn't work on `<select>` —
uses `selectOption`/radio-group `.check()` as appropriate), uploads via `setInputFiles` restricted
to a single caller-resolved path (never an arbitrary one from the field map, per §6), enforces the
120s filling timeout the same injectable way, and records ONE `apply_task_steps` row per field
action via 045's new `recordAction()` (in-stage, non-transition) — never the raw filled value,
only the taxonomy key/selector/outcome.

**Known limitation (documented, not silently assumed):** `fill-runner.ts` takes already-resolved
`valuesByKey: Record<TaxonomyFieldKey, string>` from its caller — `CareerProfile` (M3) has no
first-class "contact info" section distinct from experience/education/skills, so resolving
`firstName`/`email`/`phone` from real profile data is left to whatever wires the real trigger
(task 054's e2e spec supplies them directly as a documented stand-in). Building that resolver was
judged out of this task's own file list.
