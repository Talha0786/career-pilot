# 046 — Approval token port (single-use, 5-min TTL)

**Status:** TODO | **Milestone:** M6

## Objective
Build the single-use, short-TTL approval token ADR-003 requires: "Approval is a single-use, short-TTL token; the submit path is architecturally unreachable without it." No existing primitive fits — current auth (`apps/api/src/plugins/session.ts`) is a long-lived opaque session cookie with plain `GET`/`DEL`, which has a TOCTOU race if reused for single-use consumption. This task builds the real thing from scratch.

## Files affected
- `packages/application/src/ports/approval-token.port.ts` (new) — `ApprovalTokenPort`: `mint(applyTaskId): Promise<{ token, expiresAt }>`, `consume(token): Promise<Result<applyTaskId, 'invalid' | 'expired' | 'already_consumed'>>`. `consume` must be atomic (single round trip, no separate get-then-delete).
- `packages/infrastructure/src/auth/redis-approval-token.adapter.ts` (new) — Redis-backed, `SET token applyTaskId NX EX 300` for mint (NX guarantees no collision), and a Lua script (or `GETDEL`, available since Redis 6.2 — check the project's pinned Redis image version in `docker-compose.yml`, it's `redis:7-alpine` so `GETDEL` is available and simpler than a hand-rolled Lua script) for atomic single-use consume.
- `packages/domain/src` — decide whether token minting is triggered by an `ApplyTask.transitionTo('awaiting_review' → ... )` domain event or a plain application-layer command; document the choice.

## Dependencies
- 045 (ApplyTask aggregate — token is scoped to one ApplyTask).

## Acceptance criteria
- A token can be consumed exactly once — concurrent consume attempts on the same token: exactly one succeeds, the rest get `already_consumed` (property-test this with `Promise.all`, same rigor as the M5 budget-lock concurrency proofs).
- Expired tokens (past 5-min TTL) fail `consume` with `expired`, never silently succeed.
- Token value itself is opaque and unguessable (`randomBytes`, same standard as the existing session token in `apps/api/src/plugins/session.ts`).

## Test plan
- Unit: fake/in-memory adapter — legality of single-use semantics.
- Integration: real Redis — concurrent `Promise.all` consume race (exactly one winner, exact count assertion), TTL expiry behavior (can use a short TTL override for the test, don't wait 5 real minutes).

## Status
DONE.

**Deviation from the task file's literal suggestion (documented, not silent):** the task file
suggests `GETDEL` (Redis 6.2+) for atomic single-use consume. Tried that approach first; it cannot
satisfy this task's own acceptance criteria — `GETDEL` (or any `DEL`-based approach) makes the key
simply gone after EITHER a successful consume OR natural TTL expiry, so a second caller cannot
distinguish "already consumed" from "never existed" from "expired", but the acceptance criteria
require three genuinely distinct, independently-tested outcomes. Solved with a tombstone instead
of a deletion: the key survives past logical expiry (a `graceSeconds` window) with an explicit
`status` field, and the whole check-then-mark sequence runs as ONE Lua script (`redis.eval`), so
it's still exactly-once atomic — a single Redis command, not a GET-then-SET round trip (which would
reopen the exact TOCTOU race this primitive exists to close). Documented in full in
`redis-approval-token.adapter.ts`'s doc comment.

**Files:** `packages/application/src/ports/approval-token.port.ts` (`ApprovalTokenPort`:
`mint`/`consume`), `packages/infrastructure/src/auth/redis-approval-token.adapter.ts`
(`RedisApprovalTokenAdapter` — real Redis, Lua-script atomic consume), `packages/application/test/fakes.ts`'s
`InMemoryApprovalTokenAdapter` (mirrors the same tombstone contract for fast unit tests, reused by
task 053's tests too).

**Evidence:**
- Unit (`packages/application/test/unit/approval-token.test.ts`, fake adapter): 6/6 — mint-then-consume-once
  succeeds; second consume of the same token → `already_consumed`; unknown token → `invalid`;
  expired token (clock override, no real wait) → `expired`; two tokens for different ApplyTasks are
  independent; 25 concurrent consume attempts on the same token (`Promise.all`) → exactly 1 success.
- Integration (`packages/infrastructure/test/integration/approval-token.test.ts`, REAL Redis 7):
  7/7 — token format is `randomBytes(32).toString('hex')` (64 hex chars, same entropy standard as
  the existing session token); consume-once-then-already_consumed; unknown token → `invalid`; a
  1-second-TTL override token, waited out for real (1.1s, not the full 5 minutes) → `expired`; 30
  concurrent `consume()` calls on the same token via real `Promise.all` against real Redis → exactly
  1 success, 29 `already_consumed`; re-run on a fresh token confirms it's not a fluke; two different
  tokens under concurrent load each get their own independent winner.
- Full unit suite 555/555, `tsc --noEmit` clean, `eslint` clean, boundary lint passes.
