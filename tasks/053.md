# 053 — Submit path: exactly-once via approval token

**Status:** TODO | **Milestone:** M6

## Objective
The final, highest-consequence state transition: `approved → submitting → submitted`, gated so it is architecturally unreachable without consuming a valid single-use approval token (ADR-003's core invariant). On success, feed back into the M2-era `Application` aggregate's `applied` stage.

## Files affected
- `packages/application/src/apply/commands/submit-apply-task.ts` (new) — the ONLY code path allowed to drive `approved → submitting`. Requires the approval token; calls 046's `ApprovalTokenPort.consume(token)`; only on a successful consume does it invoke the browser-runner's actual submit action. Domain invariant (from 045) plus this being the sole call site is the "architecturally unreachable" property — no other command/route may reach `submitting`.
- `apps/browser-runner/src/submit-runner.ts` (new) — drives the actual form-submit click, `submitting → submitted` on confirmed success, `submitting → failed` on error (never silently retry a submit — a second attempt without a fresh token must be impossible by construction).
- On `submitted`: emit a domain event (per 045's `events.ts`) consumed by a new/extended worker handler that calls `Application.transitionTo('applied', { actor: 'agent' })` — using the `TransitionActor` variant the inventory confirmed already exists for exactly this purpose.
- `apps/api/src/routes/apply.ts` (extends 052's file) — the actual submit-trigger route, requiring the token from 052's approve step.

## Dependencies
- 045 (state machine), 046 (approval token), 051 (gets a task to `awaiting_review`), 052 (mints the token via approve).

## Acceptance criteria
- **Property test**: no code path reaches `submitting` without a consumed (previously-valid, now-invalid) token — this is `docs/05-playwright-design.md` §7's literal listed test ("State machine | Property tests: no path reaches `submitting` without unconsumed token").
- Exactly-once under concurrency: two simultaneous submit attempts using the same token — exactly one succeeds, the other fails with `already_consumed` (real `Promise.all` proof, same rigor as 046's own token test and M5 task 043's budget hard-stop proof).
- A successful submit transitions the linked `Application` to `applied` automatically.
- A failed submit does not leave the ApplyTask silently stuck — reaches `failed`, visible to the user.

## Test plan
- Unit: property-test-style enumeration proving no path to `submitting` bypasses token consumption.
- Integration: real Postgres+Redis, concurrent double-submit race (exact-count assertion), success→`Application.applied` wiring, failure→`failed` path.

## Status
DONE. This is the single most safety-critical piece in the whole M6 milestone and received the
most rigor of anything in this track — not rushed, no property test weakened to force a pass.

**The architectural property, three independent layers deep:**
1. **The state machine itself** (045, `apply-task-stage.ts`): `submitting` has exactly one legal
   inbound edge, from `approved`. `onlyApprovedReachesSubmitting()` asserts this against the
   transition table directly; `apply-task.test.ts`'s exhaustive 9×9 sweep proves it holds for
   every other (from, to) pair too.
2. **The sole call site** (`submit-apply-task.ts`): the ONLY file under
   `packages/application/src/apply/commands/` that ever calls `.transitionTo('submitting', ...)`.
   This isn't a code-review promise — `submit-apply-task.test.ts`'s "ARCHITECTURAL property" test
   `readFileSync`s every command file in that directory and regex-scans for the pattern, failing
   loudly if a FUTURE file ever adds a second path, before any behavioral test of that new file
   would even run. The scan's own correctness is sanity-checked against a known-true positive
   (`submit-apply-task.ts` itself must match).
3. **The token is consumed BEFORE any lookup, branch, or side effect** — an invalid/expired/
   already-consumed token means the function does nothing else, not even read the `ApplyTask` row.
   Reviewed line-by-line: `deps.approvalTokens.consume()` is genuinely the first line of real work.

**Defense in depth beyond the literal ask:** a token minted for ApplyTask A cannot be used to
submit ApplyTask B, even though it would pass `consume()` (which only knows the token, not which
task the CALLER claims it's for) — `submit-apply-task.ts` explicitly checks
`consumed.value !== applyTaskId` and rejects. Not required by the acceptance criteria as written,
added because the token's whole job is per-task consent and a cross-task reuse would defeat that
even while "technically" respecting single-use.

**A failed submit is a typed OUTCOME (`{stage: 'failed'}`), not a thrown exception** — the task
still transitions `submitting → failed` (legal), is saved, and is visible to the user; a retry with
the SAME token is impossible by construction (already consumed) — proven directly, including
against real Redis.
