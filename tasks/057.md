# 057 — Read-only MCP tools

**Status:** DONE | **Milestone:** M7

## Objective
Implement the `read`-scoped tools from `docs/04-mcp-design.md` §3: `search_jobs`, `get_job`, `get_profile`, `match_job`, `list_applications`, `get_pipeline_analytics`. Each is a thin wrapper over an existing application-layer query — no new business logic, per §1's core design constraint.

## Files affected
- `apps/mcp-server/src/tools/search-jobs.ts`, `get-job.ts`, `get-profile.ts`, `match-job.ts`, `list-applications.ts`, `get-pipeline-analytics.ts` (new, one file per tool per §5). Each wraps an existing query: job search/listing (M4), `get-job` (M4 job posting query), `get-profile` via the `CareerProfileSnapshot` shape the inventory identified, `match-job` via M5's matching query layer (`packages/application/src/matching/queries`), `list-applications` via the M2 pipeline/board query, `get-pipeline-analytics` — check if any analytics query already exists (M2/M8 roadmap mentions an "analytics dashboard" as M8 scope, so this may need a minimal funnel-stats query built here if nothing exists yet; keep it minimal, M8 owns the full dashboard).
- `packages/contracts/src` — reuse existing DTO schemas wherever they already match §3's input shapes; only add new zod schemas for genuinely new tool-specific inputs (e.g. the `{query?, filters?, limit≤50}` shape for `search_jobs` if nothing matching exists).
- **Data envelope / injection warning** (§2 rule 2): job description content returned by any tool must be wrapped so MCP clients treat it as untrusted data — implement a shared `wrapUntrustedContent(text): { content, warning }`-style envelope in `apps/mcp-server/src/untrusted-envelope.ts` (new), applied to every tool that can return JD text (`search_jobs`, `get_job`).
- Contract tests per §5: "each tool has a golden-file test (input → expected use-case call + output shape) plus an integration test against ephemeral PG."

## Dependencies
- 056 (scaffold, registry, DI, auth).

## Acceptance criteria
- Every tool in this task enforces `read` scope (no writes reachable, verified by attempting a write-shaped call and confirming it's not exposed).
- JD content returned by `search_jobs`/`get_job` is wrapped in the untrusted-content envelope with the injection warning — verified by inspecting actual tool output shape, not just documented.
- `limit≤50` and other declared input constraints in §3's table are enforced by the zod schema, not just described.

## Test plan
- Golden-file tests: input → expected use-case call + output shape, per tool.
- Integration: real Postgres, each tool's real query path exercised end-to-end via the MCP registry (not bypassing it).

## Status
DONE.

**`search_jobs` scope-down (judgment call, documented in code):** `JobPostingRepository` (M4) has no full-text search index or server-side filter predicates. `packages/application/src/discovery/queries/search-jobs.ts` fetches a bounded window (500) of the user's postings and applies `query`/`filters` (remote, location substring, minSalary, postedAfter) IN-MEMORY before truncating to the requested `limit`. This is a real, working implementation for realistic per-user posting counts, but is explicitly NOT a full-text search — a user with >500 postings and an old, unmatched target could get a false "no results." Documented as a genuine limitation in the query's own doc comment, not silently passed off as complete; a proper fix (Postgres trigram/tsvector index + WHERE-clause filters in the repository) is out of scope for a "thin wrapper" task per its own file list.

**`match_job` scope (judgment call):** §3's table lists `match_job` as `read`-scoped despite `method: 'rubric'` performing a live, budget-guarded LLM call. Honored the table literally rather than "fixing" it to `write:documents` — read scope gates PIPELINE/DOCUMENT mutation, and a recompute of a derived score has no effect on application state; the LLM budget guard (not the MCP scope system) is what actually bounds its cost. `method: 'embedding'` (the default) is a pure read of whatever score is already persisted, zero LLM cost. `packages/application/src/matching/commands/score-match.ts`'s previously-private `scoreOneCandidate` helper was made a named export (task 057) so `match-single-job.ts` (task 057's per-job scoring path) reuses the exact same LLM-call/repair/validate sequence rather than forking a second implementation — behavior-neutral change, verified by the pre-existing `score-match.test.ts` suite still passing unchanged (7/7).

**`get_pipeline_analytics` (judgment call, per the task's own instruction):** no analytics/funnel query existed anywhere before this task — M8 owns the real dashboard. Built the minimal thing the tool needs (`packages/application/src/pipeline/queries/get-pipeline-analytics.ts`): in-memory aggregate counts over `ApplicationRepository.listForUser` (same no-pagination scale assumption `get-board.ts` already makes), not a SQL aggregate. Documented as intentionally minimal in the file's own doc comment.

**Untrusted-content envelope:** `apps/mcp-server/src/untrusted-envelope.ts`'s `wrapUntrustedContent` is applied to every JD-bearing field in `search_jobs`/`get_job` (and reused by the `job` MCP resource, task 059) — `{content, warning}`, never a bare string, so a client that ignores the prose warning still gets a structurally distinct field. Verified by inspecting actual tool output shape (not just the description text) in both `apps/mcp-server/test/unit/tool-contracts.test.ts` and the dedicated `apps/mcp-server/test/unit/injection-redteam.test.ts`.

**`limit<=50` and other input constraints:** enforced by `packages/contracts/src/mcp.ts`'s zod schemas (`SearchJobsInputSchema.limit` is `z.number().int().min(1).max(50).default(20)`), checked by `McpRegistry.dispatch`'s `inputSchema.safeParse` BEFORE any handler runs (task 056's registry test suite proves invalid input never reaches a handler) — not merely described in a tool's prose description.
