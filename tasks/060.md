# 060 — Interview prep pipeline + company research

**Status:** DONE | **Milestone:** M7

## Objective
Implement `generate_interview_prep` (§3 table) backed by the two interview-prep pipelines from `docs/06-agent-design.md` §3/§5: "Interview Q&A generation | pipeline | mid | QuestionSet schema" and "Company research | bounded tool loop (max 8 tool calls): web search/fetch → synthesize brief with citations. No write tools. Output schema-validated; uncited claims dropped."

## Files affected
- `packages/contracts/src/interview-prep.ts` (new) — `QuestionSetSchema`, `CompanyResearchBriefSchema` (with a `citations` field per question/claim).
- `prompts/interview-questions/v1.md`, `prompts/company-research/v1.md` (new) — following the M5 `prompts/{task}/{version}.md` convention (034).
- `packages/application/src/interview-prep/commands/generate-questions.ts` (new) — deterministic pipeline: JD + profile facts (reuse M5 task 037's `compileFactList`) → guarded `llm.complete()` → `QuestionSetSchema` validate → one repair attempt → typed failure, same ADR-006 discipline as every prior LLM call site.
- `packages/application/src/interview-prep/commands/research-company.ts` (new) — the bounded tool loop: max 8 tool calls, web search/fetch tools (new — check if any existing infra has a web-fetch adapter; if not, build a minimal one scoped read-only to this pipeline), synthesizes a brief, drops any claim without a citation (schema-enforced, not just prompted — reject/strip uncited claims post-validation, mirroring M5 task 040's adversarial-verification rigor for the anti-hallucination contract, applied here to "must cite a source" instead of "must cite a profile fact").
- `apps/mcp-server/src/tools/generate-interview-prep.ts` (from 058, or add here if 058 stubbed it) — wires `{applicationId, kind: 'questions' | 'company_research'}` to the two commands above.
- `packages/infrastructure/src/db/migrations/0008_interview_preps.sql` (new) — `interview_preps` table (also used by 061's mock-interviewer transcripts — design the schema to cover both: `{id, application_id, kind, content jsonb, created_at}` where `kind` distinguishes `questions`/`company_research`/`mock_interview_transcript`).

## Dependencies
- 056 (MCP scaffold, though this task's commands are usable directly from application layer independent of MCP), M5 task 037 (fact-list compilation), M3 (CareerProfile).

## Acceptance criteria
- Company research brief never contains an uncited claim — test with a deliberately fabricating fake LLM response, confirm the uncited claim is stripped, not passed through.
- Tool loop is hard-capped at 8 calls (test: a pathological "keep searching forever" fake tool response still terminates at 8).
- No write tools are reachable from the research loop (read-only, per the design doc).

## Test plan
- Unit: uncited-claim-stripping with a fake LLM; tool-loop 8-call hard cap with a fake tool that always requests another call.
- Integration: real Postgres persistence of `interview_preps` rows; MCP tool round trip.

## Status
DONE.

**`interview_preps` schema (judgment call, per the task's own instruction):** one table, `kind` discriminates `questions` | `company_research` | `mock_interview_transcript` (the third kind is task 061's, designed in from the start per this task's own file-list note) — `{id, application_id, kind, content jsonb, created_at, updated_at}`, migration `0008_interview_preps.sql`. `InterviewPrepRepository.save` is upsert-by-id (needed by 061's turn-by-turn transcript growth, not by this task's own two kinds, which each create one row per invocation).

**Company research: no web-search/fetch adapter existed anywhere before this task.** Built two minimal, real (not mocked), read-only adapters scoped to exactly this pipeline (`packages/application/src/ports/research.port.ts`'s `WebSearchPort`/`WebFetchPort`, implemented by `packages/infrastructure/src/research/{web-search,web-fetch}.adapter.ts`): `HttpWebFetchAdapter` does a real HTTP GET + naive HTML-to-text stripping; `DuckDuckGoWebSearchAdapter` does a real, key-free HTML-scrape of DuckDuckGo's `/html/` endpoint (no API key required, matching ADR-006's "boots key-free by default" posture) and degrades to an EMPTY result list on any failure rather than throwing — documented in both files' doc comments as a genuine, honest limitation (screen-scraping a public page, not a supported search API; the first thing to swap for a real search API key if one is ever configured). **Neither adapter's live network behavior was integration-tested against the real internet in this session** (no test hits `duckduckgo.com`/an arbitrary URL for real) — only the pipeline logic around them (bounded loop, citation stripping, hard cap) was tested, with `FakeWebSearchPort`/`FakeWebFetchPort` doubles. This is an honest gap: the adapters' OWN wire-level correctness (do they parse DuckDuckGo's actual current HTML shape correctly) is unverified by an automated test, same class of gap the `connectors-live-canary` nightly job exists for elsewhere in this codebase — a reasonable follow-up would be a similar non-blocking nightly canary for these two adapters, not built in this session due to time.

**The bounded tool loop is a text-protocol ReAct pattern, not native function-calling (judgment call, documented in code):** `LlmPort`/`CompleteRequest` (ADR-006) has no `tools` parameter — no provider-native function-calling support exists anywhere in this codebase's LLM abstraction. `research-company.ts` implements a real, working tool loop anyway: each turn the model responds with ONE `{action: "search"|"fetch"|"final", ...}` JSON object (`prompts/company-research/v1.md`), parsed and dispatched by the orchestrating code. This is a legitimate tool-loop implementation, just not backed by a provider-native tool-calling API — documented explicitly in the command's own doc comment so it doesn't read as an oversight.

**8-call hard cap (task's explicit acceptance criterion) — a plain loop counter, not a suggestion:** `MAX_TOOL_CALLS = 8`, incremented only on `search`/`fetch` actions (a `final` action doesn't consume budget — it's the terminal decision). If the model never emits `final` within 8 tool calls, the loop stops and returns a typed `validation_failed` failure. Tested with a fake LLM whose `setFallback` always returns `{"action":"search",...}` forever — `search.calls` is asserted to be EXACTLY 8, not "at most 8" or "usually 8."

**Uncited-claim stripping is schema-enforced against ACTUALLY-OBSERVED URLs, not just prompted (task's explicit acceptance criterion):** `stripUncitedClaims` in `research-company.ts` checks every claim's citations against `seenUrls` — the set of URLs the session actually saw via a real `search`/`fetch` result this run, not merely "the LLM said it cited something." Tested with a fake LLM `final` response containing THREE claims: one correctly cited to a URL the session actually searched up (kept), one with zero citations (dropped), and one citing a URL the session NEVER actually observed (also dropped — the harder case, proving this isn't just an empty-array check) — `droppedUncitedClaimCount` asserts exactly 2, matching `docs/06-agent-design.md` §4's adversarial-verification rigor applied to "must cite a real source" instead of "must cite a profile fact."

**`generate-questions.ts` — same ADR-006 shape as every prior M5 pipeline call site:** reuses `compileFactList` (task 037) verbatim, one repair attempt on malformed JSON then a typed failure (tested: 2 always-malformed responses -> exactly 1 repair attempt -> typed failure, not a crash or an infinite retry).

**Evidence (`packages/application/test/unit/interview-prep.test.ts`, 7/7, fakes only):** generate-questions happy path + repair-then-fail path (2 tests); research-company uncited-claim-stripping (1 test, the 3-claim case above) + 8-call hard cap (1 test); the remaining 3 tests belong to task 061 (see that task's Status note). All persisted rows verified against the fake `InterviewPrepRepository`'s real upsert-by-id semantics (also proven against REAL Postgres in `packages/infrastructure/test/integration/mcp.test.ts`'s `DrizzleInterviewPrepRepository` suite, part of task 056's evidence). `generate_interview_prep`'s MCP-tool-level dispatch-by-`kind` routing (`apps/mcp-server/src/tools/generate-interview-prep.ts`) was code-reviewed but not given its own dedicated MCP-layer test beyond what registry.test.ts's catalog test proves it's registered correctly — the underlying pipelines it thinly wraps are what's actually tested, consistent with "no business logic in tool handlers."
