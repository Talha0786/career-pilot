# 058 — Write MCP tools (never-submit boundary)

**Status:** DONE (M6 integration seam stubbed — see below) | **Milestone:** M7

## Objective
Implement the `write:pipeline`/`write:documents`-scoped tools from `docs/04-mcp-design.md` §3: `update_application_stage`, `add_application_note`, `tailor_document`, `get_generation_status`, `prepare_application`. The single most important constraint in this task is §2 rule 1 and §3's "Deliberately absent" list: **no tool may submit an application, delete data, or change credentials** — `prepare_application` creates an ApplyTask only up to `awaiting_review`, never further; final approval/submit stays exclusively in the web UI per M6's task 052/053, consistent with ADR-003 ("MCP/agents cannot trigger submission").

## Files affected
- `apps/mcp-server/src/tools/{update-application-stage,add-application-note,tailor-document,get-generation-status,prepare-application}.ts` (new). `update_application_stage` wraps the existing `Application.transitionTo` use case with `actor` logged as the MCP-token identity (system actor, per the inventory's confirmation that `TransitionActor` already supports non-human actors). `tailor_document` enqueues via the existing M5 tailoring command (`packages/application/src/tailoring/commands/request-document-tailoring.ts`) and returns a job id for `get_generation_status` to poll. `prepare_application` calls M6's `start-apply-task`/`run-mapping` commands (tasks 051) but **must hard-stop the resulting ApplyTask at `awaiting_review`** — verify no code path in this tool can reach `approve`/`submit`.
- `apps/mcp-server/src/registry.ts` (056's file) — confirm the registry itself has no `submit_application`/`delete_*`/`set_credentials`/`enable_connector` tool registered anywhere, and add a registry-level test asserting the full tool name list matches exactly the documented catalog (§3 table) — a positive assertion that dangerous tools are absent, not just that present ones behave.
- Rate limiting (§5: "Rate limits per token (Redis sliding window); generation tools additionally gated by the LLM budget guard") — `tailor_document`/`prepare_application` (if mapping invokes the LLM fallback) must go through the existing `GuardedLlmPort` budget check, no bypass.

## Dependencies
- 056 (scaffold), 057 (shares the untrusted-content envelope pattern for any JD content these tools touch), M6 tasks 044/045/047/050/051 (ApplyTask machinery `prepare_application` calls into — this task can proceed once those land; if M6's track is still in progress when this task starts, coordinate/stub the ApplyTask call behind the same port interface so this task isn't fully blocked).

## Acceptance criteria
- `prepare_application` cannot, through any parameter combination, drive an ApplyTask past `awaiting_review` — test this adversarially (attempt to pass an "auto-approve" flag or similar, confirm no such parameter exists in the schema and no code path honors one even if injected).
- The full registered tool catalog exactly matches §3 (no extra tools, no missing ones) and explicitly excludes `submit_application`, `delete_*`, `set_credentials`, `enable_connector`.
- Every write tool call is rate-limited per token and (for generation tools) budget-guarded.

## Test plan
- Adversarial unit test: attempt every plausible way to make `prepare_application` submit (extra params, calling it twice, racing it against a manual approve) — all fail to reach `submitted`.
- Registry-catalog test: exact tool-name-set assertion.
- Integration: real Postgres+Redis, `update_application_stage`/`add_application_note`/`tailor_document`/`get_generation_status` round trip against real use cases.

## Status
DONE, with the M6 integration seam explicitly stubbed (documented below and in the orchestrator's own brief — M6 was still in progress in a parallel worktree when this task ran).

**The M6 integration seam (read this first — the most important design decision in this task):** `prepare_application` needs to create/advance an ApplyTask, but M6's real ApplyTask aggregate/Playwright runner (tasks 044/045/047/050/051) wasn't available in this worktree. Rather than block on M6 or half-guess its shape, a new port — `packages/application/src/ports/apply-task.port.ts`'s `ApplyTaskPort` — was designed directly against `docs/05-playwright-design.md` §3's documented state machine (`draft -> mapping -> filling -> awaiting_review -> approved -> submitting -> submitted`, or `failed`/`aborted`). **This port is the actual safety boundary, by construction, not by convention:** it declares exactly ONE method, `startAndMapToReview(input): Promise<Result<PrepareApplicationResult, DomainError>>`, whose own return type (`PrepareApplicationReachableState = 'awaiting_review' | 'failed' | 'aborted'`) structurally excludes `approved`/`submitting`/`submitted` as possible values — there is no `approve`/`submit` method anywhere on this interface, and `apps/mcp-server`'s entire dependency graph has no reference to any port that has one. A future `approve`/`submit` capability (a hypothetical `ApplyTaskApprovalPort`, used only by the web UI per ADR-003) would need to be a SEPARATE interface this process never imports — that is the seam, made explicit so whoever merges M6 knows exactly where to plug in the real adapter: swap `apps/mcp-server/src/di.ts`'s `new NotYetImplementedApplyTaskPort()` for the real Drizzle/Playwright-backed implementation of `ApplyTaskPort`; `prepare-application.ts` (the application-layer command) and the MCP tool itself should need ZERO changes. Until then, `NotYetImplementedApplyTaskPort` always returns a typed `conflict` error — verified live against the real running `mcp-server` container in this session (see task 056's Status note).

**Adversarial verification of the never-submit boundary (task's own explicit ask — "test this adversarially"):** `packages/application/test/unit/prepare-application.test.ts` (5/5): the happy path stops at `awaiting_review`; injecting `{autoApprove: true, submit: true, confirm: 'yes'}` past TypeScript with an `as unknown as` cast is silently ignored (never read, never forwarded — the ONLY thing sent to the ApplyTask backend is `{applicationId, userId}`, asserted via `toEqual`); calling it twice in a row never produces an escalated state; a structural test enumerates `ApplyTaskPort`'s own prototype methods at runtime and asserts the set is EXACTLY `['startAndMapToReview']` (so a future accidental `approve` method addition to the port would fail this test immediately, not silently become reachable); ownership is checked BEFORE the ApplyTask backend is ever touched (0 calls for another user's application). `PrepareApplicationInputSchema` (`packages/contracts/src/mcp.ts`) is `.strict()` with exactly one field — the registry's own zod validation rejects an injected extra field before the handler even runs, proven directly in `docs/mcp-injection-redteam-checklist.md` §4 / `injection-redteam.test.ts`'s payload D.

**Registry-catalog exactness (task's other explicit ask):** `apps/mcp-server/test/unit/registry.test.ts`'s "Tool catalog" describe block — the real registered tool NAME SET (via `registerAllTools`) exactly equals §3's 12 tools plus `ping` (transport plumbing), asserted with `.toEqual` against a sorted array, not a subset check; a second test explicitly asserts `submit_application`/`delete_application`/`delete_document`/`delete_profile`/`set_credentials`/`enable_connector` are absent AND that no registered name starts with `delete_`/`submit_` at all (structural, not just the five names picked by hand). A third test proves registration is provably side-effect-free (every unused port in the test's `McpDeps` is a `Proxy` that throws if any method is actually invoked — if registration ever stopped being side-effect-free, this whole describe block would fail loudly, not silently pass).

**`update_application_stage`/`add_application_note` actor identity:** both now log `actor: 'agent'` (the pre-existing `TransitionActor`/new `ApplicationNoteRepository.actor` union already had `'agent'` as a valid value, confirmed unused by any prior caller before this task) — `packages/application/src/pipeline/commands/update-stage.ts` gained an optional `actor` param (default `'user'`, so the pre-existing HTTP API route's behavior is byte-for-byte unchanged); `add-application-note.ts` is new (task 058), with its own `application_notes` table (migration `0009`) since notes have no state-machine rules and forcing them through the `Application` aggregate would mean inventing a domain event with no consumer.

**Rate limiting / budget guard (§5's other requirement):** `tailor_document` and `prepare_application` go through the SAME registry-level per-token rate limiter every other tool does (no bypass) — `tailor_document` additionally routes through `GuardedLlmPort` indirectly (it enqueues the same M5 `tailoring.document_requested` job the existing worker consumes, which is already budget-guarded; task 058 doesn't duplicate that guard, it reuses the existing enforced path, consistent with "no new business logic").

**`tailor_document` <-> `get_generation_status` polling pair (a real gap closed, not just wired):** `DocumentVersion.generationJobId` was already modeled in the domain/DB schema since task 022 but NO producer had ever populated it. Threaded it end to end (additive, optional field, zero behavior change for existing callers): `tailor_document`'s MCP tool generates a `generationJobId` (uuidv7) and passes it through `request-document-tailoring.ts` -> the BullMQ payload -> the worker's `tailor-document.handler.ts` -> `tailor-document.ts`'s `addDocumentVersion` call. `get_generation_status` polls `DocumentRepository.findByGenerationJobId` (new method, real Postgres query, added to the port + Drizzle repo + both existing fakes). **Regression found and fixed**: `apps/api/src/routes/documents.ts`'s pre-existing `POST /documents/:id/tailor` route was spreading the whole use-case output into its JSON response, so `TailorDocumentResponseSchema`'s documented `{queued: true}` contract silently gained a `generationJobId: null` field — caught by the PRE-EXISTING `apps/api/test/integration/tailoring.test.ts` test (which does an exact `.toEqual({queued:true})` check) failing after this change. Fixed by having the route explicitly narrow its response to `{queued: result.value.queued}` — the HTTP contract is unchanged; only the new MCP tool sees `generationJobId`. Re-ran the test: 5/5 passing after the fix.
