# 058 — Write MCP tools (never-submit boundary)

**Status:** TODO | **Milestone:** M7

## Objective
Implement the `write:pipeline`/`write:documents`-scoped tools from `docs/04-mcp-design.md` §3: `update_application_stage`, `add_application_note`, `tailor_document`, `get_generation_status`, `prepare_application`. The single most important constraint in this task is §2 rule 1 and §3's "Deliberately absent" list: **no tool may submit an application, delete data, or change credentials** — `prepare_application` creates an ApplyTask only up to `awaiting_review`, never further; final approval/submit stays exclusively in the web UI per M6's task 052/053, consistent with ADR-003 ("MCP/agents cannot trigger submission").

## Files affected
- `apps/mcp-server/src/tools/{update-application-stage,add-application-note,tailor-document,get-generation-status,prepare-application}.ts` (new). `update_application_stage` wraps the existing `Application.transitionTo` use case with `actor` logged as the MCP-token identity (system actor, per the inventory's confirmation that `TransitionActor` already supports non-human actors). `tailor_document` enqueues via the existing M5 tailoring command (`packages/application/src/tailoring/commands/request-document-tailoring.ts`) and returns a job id for `get_generation_status` to poll. `prepare_application` calls M6's `start-apply-task`/`run-mapping` commands (tasks 051) but **must hard-stop the resulting ApplyTask at `awaiting_review`** — verify no code path in this tool can reach `approve`/`submit`.
- `apps/mcp-server/src/registry.ts` (056's file) — confirm the registry itself has no `submit_application`/`delete_*`/`set_credentials`/`enable_connector` tool registered anywhere, and add a registry-level test asserting the full tool name list matches exactly the documented catalog (§3 table) — a positive assertion that dangerous tools are absent, not just that present ones behave.
- Rate limiting (§5: "Rate limits per token (Redis sliding window); generation tools additionally gated by the LLM budget guard") — `tailor_document`/`prepare_application` (if mapping invokes the LLM fallback) must go through the existing `GuardedLlmPort` budget check, no bypass.

## Dependencies
- 056 (scaffold), 057 (shares the untrusted-content envelope pattern for any JD content these tools touch), M6 tasks 044/045/047/050/051 (ApplyTask machinery `prepare_application` calls into — this task can proceed once those land; if M6's track is still in progress when this task starts, coordinate/stub the ApplyTask call behind the same port interface so this task isn't fully blocked).

## Acceptance criteria
- `prepare_application` cannot, through any parameter combination, drive an ApplyTask past `awaiting_review` — test this adversarially (attempt to pass an "auto-approve" flag or similar, confirm no such parameter exists in the schema and no code path honors one even if injected).
- The full registered tool catalog exactly matches §3 (no extra tools, no missing ones) and explicitly excludes `submit_application`, `delete_*`, `set_credentials`, `enable_connector`.
- Every write tool call is rate-limited per token and (for generation tools) budget-guarded.

## Test plan
- Adversarial unit test: attempt every plausible way to make `prepare_application` submit (extra params, calling it twice, racing it against a manual approve) — all fail to reach `submitted`.
- Registry-catalog test: exact tool-name-set assertion.
- Integration: real Postgres+Redis, `update_application_stage`/`add_application_note`/`tailor_document`/`get_generation_status` round trip against real use cases.
