# 055 — Degradation ladder + copy-paste-assist mode

**Status:** TODO | **Milestone:** M6

## Objective
Close out M6's explicitly-named risk mitigation: "if mapper accuracy stalls, ship copy-paste-assist mode as the M6 floor" (roadmap) and the anti-fragility posture from `docs/05-playwright-design.md` §5: selector-map versioning, structured `MappingFailure` telemetry, and the full degradation ladder "known-ATS map → heuristics → LLM map → copy-paste assist mode (side-panel showing user's values to paste manually). The product never dead-ends."

## Files affected
- `apps/browser-runner/src/mapping-failure-telemetry.ts` (new) — structured `MappingFailure` record (which stage failed, taxonomy field, anonymized form signature — no PII in the telemetry itself), written wherever 048/049/050 currently fail silently or throw.
- `apps/web/src/app/apply/copy-paste-assist/page.tsx` (new) — the floor mode: when mapping produces zero usable fields (all three stages failed/low-confidence), instead of dead-ending the ApplyTask, surface a side panel showing the user's relevant profile values so they can paste them manually into the real ATS site themselves.
- `packages/application/src/apply/commands/run-mapping.ts` (051's file) — extend so a total-mapping-failure outcome routes to a new terminal-ish state (or reuses `awaiting_review` with a "manual assist" flag) rather than `failed`, consistent with "never dead-ends."
- `apps/browser-runner/src/ats-maps/*.ts` (048's files) — add explicit version tags per adapter (design doc: "Selector maps versioned; nightly canary tasks run against ATS sandbox/demo forms; failures flip the ATS adapter to `DEGRADED`").
- `.github/workflows/nightly.yml` — add a canary job running 048's fixture tests nightly (the design doc's "nightly canary tasks... failures flip the ATS adapter to DEGRADED" — a lightweight version against fixtures is acceptable if live ATS sandbox access isn't available; document which was actually built).

## Dependencies
- 048, 049, 050 (all three mapping stages must exist to have a ladder to degrade through), 051 (mapping orchestration to extend).

## Acceptance criteria
- A form no adapter/heuristic/LLM stage can map at all still produces a usable outcome for the user (copy-paste-assist), never a bare "failed" dead-end with no recovery path — this is the literal roadmap risk mitigation, test it directly (fixture form with zero mappable fields).
- `MappingFailure` telemetry is queryable/inspectable (even just via a DB table or log aggregation point) — this is the "triage dashboard" feed the design doc mentions; a full dashboard UI is out of scope for M6, just the structured data feed.
- ATS adapter `DEGRADED` state is representable and causes the pipeline to skip straight to heuristics for that platform going forward (avoid repeatedly trying a known-broken adapter).

## Test plan
- Unit/integration: forced total-mapping-failure fixture → copy-paste-assist outcome, not `failed`.
- Unit: `MappingFailure` telemetry recorded on each stage's failure path.

**The core "never dead-ends" property — the actual point of this task:**
`run-mapping.ts` (051) now computes `manualAssistRequired: usableFields.length === 0` (a field
that's only ever surfaced-unfilled, i.e. `neverAutoFill`, doesn't count as "usable" — a form with
only EEO fields detected still needs manual assist for anything real). When true, the task is
recorded via `recordAction('field-map-computed', {..., manualAssistRequired: true})` and stays in
`mapping` — **critically, NOT `failed`** — directly proven by two unit tests (a form where every
stage returns nothing, and a form where only a sensitive field was ever detected, both assert
`reloaded.stage === 'mapping'`, never `'failed'`).
`apps/web/src/app/apply/copy-paste-assist/page.tsx` is the UI this outcome routes toward — real,
compiling, but its live-values read endpoint doesn't exist yet (documented in the page's own
comment; same category of honest gap as task 052's `FieldDiffView` wiring note).

**`MappingFailure` telemetry:** implemented as structured `pino` logging
(`apps/browser-runner/src/mapping-failure-telemetry.ts`), not a new Postgres table — the task
file's own phrasing explicitly allows "just a log aggregation point," and every field
(`event: 'mapping_failure'`, stage, taxonomy field, an ANONYMIZED form signature — field count +
tag-type histogram only, never raw values/HTML) is greppable/aggregatable by any standard log
pipeline. A DB-backed version is a reasonable follow-up if a real triage dashboard gets built.

**ATS adapter `DEGRADED` state:** `apps/browser-runner/src/ats-adapter-health.ts`
(`AtsAdapterHealthRegistry`) — in-memory (documented limitation: resets on process restart, not
shared across instances; a DB-backed version is the natural follow-up, same posture as the
telemetry choice above), `markDegraded`/`markHealthy`/`isHealthy` per ATS key, independent per
adapter (marking `lever` degraded never touches `greenhouse`'s health).

**Nightly canary (documented honestly, not oversold):** `.github/workflows/nightly.yml`'s new
`ats-selector-canary` job runs task 048's OWN recorded-fixture Playwright suite
(`apps/browser-runner/test/ats-maps.spec.ts`) nightly, non-blocking. This is explicitly the
"lightweight fixture version," NOT a live-ATS-sandbox canary — no real Greenhouse/Lever/Ashby/
Workday sandbox account is obtainable for an OSS project, and the job's own failure-notification
text says so, so a failure here is correctly understood as "this repo's own selector maps
regressed," not "a real ATS platform changed its DOM."

**Version tags:** each of 048's four `AtsMap`s already carries a `version` field
(`'2026.07.1'`) — the versioning half of "Selector maps versioned" predates this task (048); this
task's job was the canary + DEGRADED-tracking half, which is what's new here.
