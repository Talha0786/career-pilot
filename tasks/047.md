# 047 — apps/browser-runner scaffold + Playwright + internal task API

**Status:** TODO | **Milestone:** M6

## Objective
Stand up the `browser-runner` service per `docs/05-playwright-design.md` §2 and §6: a separate process for Chromium isolation, one fresh browser context per ApplyTask, internal task API bound to the compose network only (never internet-exposed), stateless (all state in Postgres via 044/045).

## Files affected
- `apps/browser-runner/` (new app, closest analog is `apps/worker` per the inventory — queue-consumer shape, no published port) — `package.json`, `tsconfig.json`, `Dockerfile`, `src/main.ts`.
- Root `package.json` / `pnpm-workspace.yaml` — no change needed, `apps/*` glob auto-discovers it (confirmed in inventory).
- Add `playwright` (+ `@playwright/test` if task 054's e2e work needs it — coordinate naming so 054 doesn't duplicate the dependency) to `apps/browser-runner/package.json`. Note: Playwright needs browser binaries installed in the Docker image (`npx playwright install --with-deps chromium`) — add this to `apps/browser-runner/Dockerfile`.
- `apps/browser-runner/src/task-api.ts` (new) — minimal internal HTTP API (Fastify, matching `apps/api`'s style) authenticated with a service token (env var, not the user session system), bound to `0.0.0.0` inside the compose network but **not published to the host** in `docker-compose.yml` (no `ports:` entry, unlike `postgres`/`redis`/`caddy` — per the inventory's finding that this is the one service that must stay internal-only).
- `docker-compose.yml` — add `browser-runner` service, shaped like `worker` (`depends_on: postgres/redis/migrate`, `DATABASE_URL`/`REDIS_URL` env, `extra_hosts: host.docker.internal` if it needs the local LLM endpoint for task 050's fallback mapper).
- Security posture from `docs/05-playwright-design.md` §6: container read-only rootfs, no volume mounts except a tmp screenshot dir, seccomp default, downloads disabled. Apply what's practical at the Dockerfile/compose level now; document what's deferred.

## Dependencies

## Acceptance criteria

- A trivial internal task-API smoke request succeeds only with the service token; fails without one.
- Playwright launches a real headless Chromium inside the container (smoke test: navigate to a local fixture page, read its title) — proves the Docker image actually has working browser binaries, the single most common Playwright-in-Docker failure mode.

- Integration: Playwright launches against a trivial static HTML fixture inside the container.

**Real bug found and fixed during this task's own Docker verification (not merely
anticipated):** the first Dockerfile draft installed Playwright browsers via a version-pinned
`npx playwright@1.49.1 install --with-deps chromium` run BEFORE `node_modules` was copied into the
image. That downloaded browser build v1148 (matching CLI 1.49.1), but the ACTUAL `playwright`
package pnpm resolved from `package.json`'s `^1.49.1` was 1.61.1, which expects browser build
v1228 — `browserType.launch: Executable doesn't exist at .../chromium_headless_shell-1228/...`,
caught by hitting `/internal/smoke/browser` against the real built image, exactly the "browser
launches" failure mode this task's own spec calls out as the most common one, just a different
flavor (version drift) than the "missing system libs" one originally anticipated. Fixed by moving
the install to AFTER `node_modules` is copied and running it via `pnpm --filter
@careerpilot/browser-runner exec playwright install --with-deps chromium` (resolves whatever
version actually ships in the image, no separate version number to keep in sync by hand). Also
chose Debian (`node:22-slim`), not Alpine, for the base image up front — Playwright's Chromium
does not reliably launch against musl libc — documented in the Dockerfile's own header comment.
