# 045 — Domain: ApplyTask aggregate + state machine

**Status:** TODO | **Milestone:** M6

## Objective
Implement the `ApplyTask` aggregate enforcing the state machine from `docs/05-playwright-design.md` §3: `draft → mapping → filling → awaiting_review → approved → submitting → submitted`, with `failed`/`aborted` reachable from `mapping`/`filling`/`awaiting_review`. This is the domain-layer core that task 053's exactly-once submit guard and task 052's review UI both depend on.

## Files affected
- `packages/domain/src/apply/apply-task.ts` (new) — `ApplyTask` aggregate root, mirrors the `Application` aggregate's shape (`packages/domain/src/pipeline/application.ts`): private `#newSteps`/`pullSteps()` for append-only step recording (same pattern as `Application`'s `#newTransitions`/`pullTransitions()`), a `transitionTo(toStage, action?, redactedPayload?)` method that throws/returns a `Result` on illegal transitions per the state diagram above.
- `packages/domain/src/apply/apply-task-stage.ts` (new) — the stage enum + a pure `isLegalTransition(from, to): boolean` function, unit-testable in isolation (mirrors `packages/domain/src/pipeline/stage.ts`).
- `packages/domain/src/apply/events.ts` (new, if ApplyTask needs domain events for the outbox — e.g. `ApplyTaskSubmittedEvent` to trigger `Application.transitionTo('applied')`; check how `packages/domain/src/profile/events.ts` (035) wired profile→matching for the cross-aggregate event pattern to copy).
- `packages/application/src/ports/repositories.ts` — add `ApplyTaskRepository` port.
- `packages/infrastructure/src/db/repositories/drizzle-apply-task.repository.ts` (new), backed by 044's tables.

## Dependencies
- 044 (schema).

## Acceptance criteria
- Illegal transitions (e.g. `draft → submitted` directly, or any transition out of `submitted`/`failed`/`aborted`) are rejected by the aggregate itself — a domain invariant, not just an application-layer check (this is the "architecturally unreachable without it" property ADR-003 requires for the later submit gate).
- Every transition produces exactly one `apply_task_steps` row when persisted.
- `submitted` is terminal — no further transitions possible.

## Test plan
- Unit: full legal-transition-graph coverage (table-driven test enumerating every (from, to) pair, asserting accept/reject matches the documented diagram) — this is the property task 053's later "no path reaches `submitting` without unconsumed token" test builds on, so get the legality table exactly right here.
- Integration: real Postgres persist/reload round-trip, append-only step history correctly ordered.

**State machine (judgment call, documented in `apply-task-stage.ts`'s own doc comment, not
silently diverged):** the design doc's diagram draws failed/aborted branches from `filling`,
`awaiting_review`, and `submitting` only; this task's own prose says
"mapping/filling/awaiting_review". Reconciled by including **all four** (`mapping`, `filling`,
`awaiting_review`, `submitting`) — task 053's acceptance criterion explicitly requires
`submitting → failed` to exist ("a failed submit... reaches `failed`"). Also added `draft →
aborted` and `approved → aborted` so every non-terminal stage has at least one safe exit; `submitting`
deliberately has **no** `aborted` exit — once a submit attempt is in flight the only two honest
outcomes are `submitted` or `failed`, never a lie that it was "aborted" while a real HTTP request to
a real ATS may already be in flight. A pure `onlyApprovedReachesSubmitting()` function
was added specifically so task 053's later property test could assert the ADR-003 invariant
against the transition table directly, not just against runtime behavior.

**Files:** `packages/domain/src/apply/apply-task-stage.ts` (stage enum + `isLegalTransition` +
`onlyApprovedReachesSubmitting`), `apply-task.ts` (`ApplyTask` aggregate — `transitionTo` is the
ONLY mutator of stage, mirrors `Application`'s `#newTransitions`/`pullTransitions()` pattern via
`#newSteps`/`pullSteps()`; also added `recordAction()` — an in-stage, non-transition step-append
method discovered necessary during task 051's implementation, since `apply_task_steps` needs to
record per-field-fill browser actions WITHIN the `filling` stage, not just stage transitions;
`transitionTo('filling')` from `filling` would be an illegal self-transition, so a separate
same-stage recording path was added, documented in that method's own comment), `events.ts`
(`APPLY_TASK_EVENTS` — `CREATED`/`STAGE_CHANGED`/`SUBMITTED`, the last one emitted automatically
whenever a transition's `toStage === 'submitted'`, consumed by task 053's worker handler for the
`Application.applied` wire). `packages/application/src/ports/repositories.ts` — added
`ApplyTaskRepository`. `packages/infrastructure/src/db/repositories/drizzle-apply-task.repository.ts`
— `save()` upserts current stage AND drains+appends `pullSteps()` in the same call (never a
separate "persist steps" path); also drains `pullEvents()` into the outbox if an `OutboxPort` is
supplied to the constructor (optional — see that file's own "KNOWN LIMITATION" doc comment: this
drain is a SEPARATE call after the row writes commit, not inside the same Postgres transaction the
way `DrizzleUnitOfWork`'s `TransactionContext` guarantees for every other aggregate — `ApplyTask`
isn't wired into `TransactionContext`, out of scope for this milestone's time budget, flagged for
follow-up).
