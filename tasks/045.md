# 045 — Domain: ApplyTask aggregate + state machine

**Status:** TODO | **Milestone:** M6

## Objective
Implement the `ApplyTask` aggregate enforcing the state machine from `docs/05-playwright-design.md` §3: `draft → mapping → filling → awaiting_review → approved → submitting → submitted`, with `failed`/`aborted` reachable from `mapping`/`filling`/`awaiting_review`. This is the domain-layer core that task 053's exactly-once submit guard and task 052's review UI both depend on.

## Files affected
- `packages/domain/src/apply/apply-task.ts` (new) — `ApplyTask` aggregate root, mirrors the `Application` aggregate's shape (`packages/domain/src/pipeline/application.ts`): private `#newSteps`/`pullSteps()` for append-only step recording (same pattern as `Application`'s `#newTransitions`/`pullTransitions()`), a `transitionTo(toStage, action?, redactedPayload?)` method that throws/returns a `Result` on illegal transitions per the state diagram above.
- `packages/domain/src/apply/apply-task-stage.ts` (new) — the stage enum + a pure `isLegalTransition(from, to): boolean` function, unit-testable in isolation (mirrors `packages/domain/src/pipeline/stage.ts`).
- `packages/domain/src/apply/events.ts` (new, if ApplyTask needs domain events for the outbox — e.g. `ApplyTaskSubmittedEvent` to trigger `Application.transitionTo('applied')`; check how `packages/domain/src/profile/events.ts` (035) wired profile→matching for the cross-aggregate event pattern to copy).
- `packages/application/src/ports/repositories.ts` — add `ApplyTaskRepository` port.
- `packages/infrastructure/src/db/repositories/drizzle-apply-task.repository.ts` (new), backed by 044's tables.

## Dependencies
- 044 (schema).

## Acceptance criteria
- Illegal transitions (e.g. `draft → submitted` directly, or any transition out of `submitted`/`failed`/`aborted`) are rejected by the aggregate itself — a domain invariant, not just an application-layer check (this is the "architecturally unreachable without it" property ADR-003 requires for the later submit gate).
- Every transition produces exactly one `apply_task_steps` row when persisted.
- `submitted` is terminal — no further transitions possible.

## Test plan
- Unit: full legal-transition-graph coverage (table-driven test enumerating every (from, to) pair, asserting accept/reject matches the documented diagram) — this is the property task 053's later "no path reaches `submitting` without unconsumed token" test builds on, so get the legality table exactly right here.
- Integration: real Postgres persist/reload round-trip, append-only step history correctly ordered.
