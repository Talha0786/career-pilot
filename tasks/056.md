# 056 — apps/mcp-server scaffold + transports + bearer-token auth

**Status:** DONE | **Milestone:** M7

## Objective
Stand up the MCP server per `docs/04-mcp-design.md` §1/§5: a thin interface layer over the existing application-layer use cases (same DI container as `apps/api`, no business logic in tool handlers), two transports (stdio for local desktop clients, Streamable HTTP/SSE for remote), both authenticated. `@modelcontextprotocol/sdk` is not yet a dependency anywhere — this is a from-scratch build.

## Files affected
- `apps/mcp-server/` (new app — closest analog is `apps/api`'s HTTP style per the inventory, plus a stdio entrypoint) — `package.json` (add `@modelcontextprotocol/sdk`), `tsconfig.json`, `Dockerfile`, `src/main-stdio.ts`, `src/main-http.ts`.
- `apps/mcp-server/src/registry.ts` (new) — tool registry composing `{name, description, inputSchema, handler}` per tool file, per §5's "One file per tool exporting {name, description, inputSchema, handler}; registry composes them."
- `apps/mcp-server/src/di.ts` (new) — reuses the same composition-root pattern `apps/api/src/app.ts` already uses for `AppDeps`, so handlers get identical budget-guard/validation/audit behavior across HTTP and MCP interfaces (§5: "guarantees budget checks, validation, and audit behave identically across interfaces").
- `packages/infrastructure/src/auth/mcp-token.adapter.ts` (new) — bearer-token auth, separate from `apps/api`'s session-cookie system (the inventory confirmed no non-cookie auth path currently exists — MCP clients can't hold a browser cookie). Tokens minted with scopes: `read`, `write:pipeline`, `write:documents` (§4); default token is read-only.
- `apps/api/src/routes/mcp-tokens.ts` (new, or extend an existing settings route) — a user-facing way to mint/revoke MCP bearer tokens from the web UI/API (needed for someone to actually get a token to use in Claude Desktop).
- `docker-compose.yml` — add `mcp-server` service for the HTTP/SSE transport (stdio is invoked directly by desktop clients, not a compose service).

## Dependencies
None from M6 (M7 depends on M5 only, per the roadmap — confirmed independent of the M6 track).

## Acceptance criteria
- Both transports boot; a trivial no-op tool call round-trips over stdio and over HTTP/SSE.
- A request with no token, an invalid token, or a token lacking the required scope for a given tool is rejected — verified per scope tier, not just "any token works."
- Every tool call writes an `audit_log` entry (§2 rule 3: "Every tool call → `audit_log`") — enforced at the registry/dispatch layer so no individual tool handler can forget it.

## Test plan
- Unit: scope-enforcement matrix (token scope × tool required scope → allow/deny).
- Integration: real Postgres+Redis, stdio round-trip, HTTP/SSE round-trip, `audit_log` row written per call.

## Status
DONE.

**Registry-as-safety-boundary (judgment call):** the design doc's §5 says handlers should share "the same DI container as apps/api." Rather than literally reuse `apps/api`'s `buildApp(AppDeps)` (a Fastify-shaped composition root), `apps/mcp-server` has its own parallel `McpDeps`/`buildRegistry` composition root (`apps/mcp-server/src/di.ts`) that constructs the SAME real adapters (`DrizzleApplicationRepository`, `GuardedLlmPort`, etc.) apps/api uses. Reasoning: `AppDeps` is Fastify-request-shaped (routes, preHandlers, WS hub) and MCP tool dispatch has a fundamentally different auth model (bearer token, not session cookie) and a different failure-mapping contract (McpToolError codes, not HTTP status + problem+json) — forcing both through one literal shared object would mean threading MCP-only concerns into `apps/api/src/app.ts` for no benefit. What IS literally shared: every repository/port implementation class (`packages/infrastructure`), so "budget checks, validation, and audit behave identically" is true at the ADAPTER level, which is where it actually matters (a `GuardedLlmPort` instance behaves identically no matter which composition root constructed it).

**Auth/dispatch design:** `apps/mcp-server/src/registry.ts`'s `McpRegistry` is the ONE place every tool call passes through (both transports call `registry.dispatch(bearerToken, name, input)`, never a tool handler directly) — auth → scope → rate-limit → zod-validate → handler → audit, in that order, with an audit row written on EVERY branch including rejections. `McpTokenAdapter` (`packages/infrastructure/src/auth/mcp-token.adapter.ts`) stores only a SHA-256 hash of the token (plaintext shown once at mint time, `cpmcp_` prefix); `apps/api/src/routes/mcp-tokens.ts` is the mint/list/revoke surface, default-scoped `['read']`.

**Transport implementation (judgment call):** built on `@modelcontextprotocol/sdk`'s `McpServer` high-level API (not the lower-level `Server` class) via a shared bridge (`apps/mcp-server/src/sdk-bridge.ts`'s `attachRegistryToServer`) that both `main-stdio.ts` and `main-http.ts` call identically — the only difference between transports is where the bearer token comes from (an `MCP_TOKEN` env var for stdio, since a local desktop client has no HTTP header to carry one; the `Authorization` header per-request for HTTP). HTTP runs STATELESS (`sessionIdGenerator: undefined`, the SDK's own documented pattern) — a fresh `McpServer`+transport per request, all backed by the same long-lived `McpRegistry`/DB pool, so this is cheap (closures only), not a new DB connection per call. Two narrow `as unknown as X` casts were needed in `main-http.ts` where the SDK's own shipped type declarations aren't compatible with this repo's `exactOptionalPropertyTypes: true` (documented inline at each cast — a real friction between this repo's strictness and a third-party library's types, not a type-safety gap in this project's own code).
