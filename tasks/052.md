# 052 — Screencast + batch review queue UI

**Status:** TODO | **Milestone:** M6

## Objective
Web UI for `awaiting_review`: live CDP screencast of the browser-runner's context plus a field-value diff, and the batch review queue ADR-003 requires ("the UI supports a review queue where the user inspects N pre-filled applications and approves them in a batch... each approval still mints its own single-use token and each submission is still individually consented to").

## Files affected
- `apps/api/src/ws/hub.ts` — extend `HubEvent` (currently `JobEmbeddedEvent | DocumentTailoredEvent`) with an `ApplyTaskScreencastEvent`/`ApplyTaskUpdatedEvent` variant; reuse the existing `ConnectionHub`/`requireAuth` cookie-session pattern (per the inventory, no new transport library needed). Note the existing hub scopes by `userId` only, not by task — since ApplyTasks are user-owned this is acceptable, but confirm no cross-task leakage in the payload.
- `apps/browser-runner/src/screencast.ts` (new) — CDP screencast frames piped up to the API (via Redis pub/sub or a direct internal call — `browser-runner` has no existing pub/sub path to `apps/api`; pick the simplest that fits the existing infra, e.g. publish to a Redis channel `apps/api`'s WS layer subscribes to, document the choice).
- `apps/web/src/app/apply/review/page.tsx` (new) — the batch review queue: lists all `awaiting_review` ApplyTasks for the user, per-task field diff (mapped value vs. taxonomy field vs. what will be submitted), approve/reject actions.
- `apps/web/src/components/{ApplyReviewCard,FieldDiffView}.tsx` (new).
- `apps/api/src/routes/apply.ts` (new) — `GET /apply-tasks?stage=awaiting_review` (list for queue), `POST /apply-tasks/:id/approve` (calls 046's `ApprovalTokenPort.mint`, transitions `awaiting_review → approved`), `POST /apply-tasks/:id/reject` (transitions to `aborted`).
- Sensitive fields (EEO/demographic) must render in the diff **unfilled and clearly marked** per §4's "never auto-filled; surfaced to the user untouched" — this is a UI-level restatement of the same invariant 048/049/050 enforce upstream; verify it isn't silently dropped from the diff view.

## Dependencies
- 051 (produces the `awaiting_review` state and diff data this UI reads), 046 (approval token minted on approve).

## Acceptance criteria
- A user can review multiple `awaiting_review` tasks in one sitting and approve each individually — each approval mints its own token (verify via 046's port, not a shared/batch token).
- Screencast renders live frames from a real browser-runner context during `mapping`/`filling` (not just a static screenshot) — smoke-testable in a real browser.
- Sensitive fields are visibly unfilled/flagged in the diff, never silently pre-populated.
- 30-min `awaiting_review` timeout (design doc §3) surfaces in the UI (task disappears from the active queue / shows as aborted) once it fires.

## Test plan
- Component/unit: diff rendering with fixture data including a sensitive field, confirming it renders unfilled+flagged.
- Integration: API route round-trip (list, approve mints token, reject aborts).
- Manual/browser verification (per this session's standing rule for UI changes): actually open the review page in a browser against the running compose stack and confirm the golden path.
