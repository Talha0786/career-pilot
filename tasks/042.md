# 042 — Intelligence eval harness (nightly CI gate)

**Status:** DONE | **Milestone:** M5

## Objective
Implement `docs/06-agent-design.md` §6: a golden-set eval harness tracking parse field-accuracy, mapper P0 accuracy, tailoring unsupported-claim rate, and rubric-score correlation with human-labeled samples, run nightly in CI (not per-PR — cost) against pinned models. This is the roadmap's explicit M5 acceptance criterion ("eval gates from agent-design §6 pass") and the regression gate for the anti-hallucination contract ("0 unsupported claims surviving verification").

## Files affected
- `packages/intelligence-evals/` (new workspace package) — `package.json`, `tsconfig.json`, added to `pnpm-workspace.yaml`'s `packages:` list (mirror how `docs/eval` was formalized during the M3/M4 merge fixes — but this time give it a proper `package.json` from the start, not a bolt-on fix).
- `packages/intelligence-evals/fixtures/` — golden (profile, job-description) pairs, including **deliberate trap prompts** per docs/06 §4.5 (a JD demanding a certification the profile lacks — the eval must prove the tailoring pipeline does NOT fabricate it).
- `packages/intelligence-evals/src/run-tailoring-eval.ts` — runs 039+040 against fixtures, asserts 0 unsupported claims survive verification on the trap-prompt fixtures specifically (this is the hard gate).
- `packages/intelligence-evals/src/run-matching-eval.ts` — runs 038 against fixtures with human-labeled expected scores, computes correlation (Pearson or Spearman — pick one, document the choice), tracks over time (append results to a checked-in or artifact-uploaded results log — decide storage: simplest is a timestamped JSON written to a CI artifact, per-run, not a growing checked-in file).
- `packages/intelligence-evals/src/run-resume-import-eval.ts` — migrate the existing `docs/eval/resume-import-benchmark/score.ts` logic here (or have this package import/wrap it) so all M5+ evals live in one CI-wired place; keep the 97.58%-accuracy fixture corpus from task 023, don't regress it.
- `.github/workflows/nightly.yml` — new job (alongside the existing `ollama-contract` and `connectors-live-canary` jobs) running the eval suite against pinned models, failing the workflow (not `continue-on-error`, unlike the live-canary job — this one is a real regression gate) if the tailoring trap-prompt gate or a defined accuracy threshold regresses.
- `packages/intelligence-evals/README.md` (or inline in package) — document how to add a new fixture, what "pinned models" means here and where the pin lives.

## Dependencies
- 038 (matching), 039 (tailoring), 040 (claim verification) — the eval harness runs all three pipelines.

## Acceptance criteria
- `pnpm --filter @careerpilot/intelligence-evals run eval` runs locally and produces a clear pass/fail summary (mirror `docs/eval/resume-import-benchmark/score.ts`'s existing PASS/BELOW-GATE output style).
- Nightly CI job runs the full suite against pinned models and fails the workflow run on regression of the tailoring 0-unsupported-claims gate.
- Boundary lint passes for the new package (respect Clean Architecture import rules — check `scripts/verify-boundary-enforcement.mjs` for what it allows a workspace package outside `apps/`/`packages/{domain,application,...}` to import).
- The existing resume-import benchmark's 97.58% accuracy does not regress after the migration into this package.

**Two real production bugs found and fixed by this task's own eval runs — not by
inspection, by literally watching the pipeline fail against a real model:**

1. **Missing `response_format: json_object` hint.** None of `score-match.ts`,
   `tailor-document.ts`, or `verify-claims.ts` ever passed `jsonSchema` on their
   `llm.complete()` calls, so `OpenAiCompatibleLlmAdapter` never set
   `response_format: {type:'json_object'}` — every structured-output call relied on prompt
   instructions alone. Fine with GPT-4-class instruction-following; with the key-free default
   `llama3.1` (8B), 3 of 5 matching fixtures failed with "not valid JSON" / schema-mismatch
   errors even after the ADR-006 one-repair-attempt. Fix: pass `jsonSchema: {type:'object'}`
   at all three call sites (the field's CONTENT is unused by the adapter — only its presence
   toggles JSON mode, per `llm.port.ts`'s own doc comment on `jsonSchema` being "a hint, not a
   guarantee").
2. **Prompt frontmatter `temperature` was parsed but never wired through.**
   `PromptTemplate.frontmatter.temperature` has existed since task 034 and every M5 prompt
   file declares one (`verify-claims/v1.md` deliberately declares `0.0` — the adversarial
   audit should be conservative/deterministic) — but `CompleteRequest` (`llm.port.ts`) had no
   `temperature` field at all, so it was silently dropped at every call site, leaving every
   provider on its own default (~0.8 for Ollama). Root-caused by reproducing a real tailoring-eval
   failure (`verify-claims`'s JSON response parsed to a bare string instead of an object)
   directly against the live endpoint outside the harness, then confirming an identical prompt
   re-run without a temperature pin was the variable. Fix: added `temperature?: number` to
   `CompleteRequest`, forwarded it in `OpenAiCompatibleLlmAdapter.complete()`, and threaded
   each call site's own loaded `PromptTemplate.frontmatter.temperature` through
   (`score-match.ts`, `tailor-document.ts`'s `generateOnce`, `verify-claims.ts`).
   After both fixes: matching went from 2/5 to 5/5 fixtures scoring cleanly; tailoring went
   from 2/3 to 3/3 fixtures passing (the previously-erroring control fixture now completes
   cleanly). Full unit suite re-verified 413/413, full integration suite 120/120, `tsc --noEmit`
   clean across all 12 workspace packages (`turbo run typecheck`), root `eslint .` clean (only
   6 pre-existing unrelated warnings), boundary lint (`verify-boundary-enforcement.mjs`) still
   passes — these were real, narrowly-scoped production fixes, not the eval gate being loosened
   to paper over them (per this task's own instruction not to do that).

**Known gaps / judgment calls, documented rather than hidden:**
- The matching/tailoring golden sets are intentionally small (5 and 3 fixtures) to keep a full
  local eval run tractable on CPU-bound local inference (~10-15 minutes for the combined
  suite). `README.md`'s "Adding a fixture" section documents the format for growing both sets;
  the correlation gate is deliberately soft until the corpus is larger.
- `eval:matching`/`eval:tailoring` require a reachable OpenAI-compatible endpoint and fail
  loudly (not silently) if none is reachable, by design (see `harness.ts`'s doc comment for why
  a scripted stand-in would make the trap-prompt gate meaningless).
- The two production fixes above (`jsonSchema` hint, `temperature` threading) are real
  reliability/determinism improvements to the M5 pipelines discovered BY this task's own eval
  run, not scope creep — same posture as the task-041 Dockerfile bug and the task-043 budget-
  estimate fix: found via genuinely exercising the system, fixed in place, documented here.
- **Residual non-zero transient-error rate with the key-free default model, documented not
  hidden:** even after both fixes, llama3.1 8B under back-to-back CPU load occasionally
  exhausts ADR-006's one-repair-attempt budget on the `verify-claims` call and surfaces a typed
  `invalid_response` error rather than a clean result (observed once across ~4 real tailoring-eval
  trials in this session). This is the system correctly failing safe (a typed error the caller
  must handle, e.g. by re-queuing — not a silent pass, not a leaked claim), and is precisely the
  scenario ADR-006 anticipates the BYO-cloud-key path for quality-critical production traffic.
  Not treated as a task-042 gate failure to chase down further, since the actual thing this task
  gates on — 0 unsupported claims surviving verification unflagged — held on every single run,
  including the one that errored. A future task could raise `MAX_REGENERATION_RETRIES`-style
  resilience for the verify-claims call specifically, or default production to a stronger
  BYO-key model, but that's a deliberate scope boundary for this task, not an oversight.
