# 059 — MCP resources + prompts

**Status:** DONE | **Milestone:** M7

## Objective
Implement the resources and prompts catalog from `docs/04-mcp-design.md` §4: read-only projections for context loading (`careerpilot://profile/{id}`, `careerpilot://job/{id}`, `careerpilot://application/{id}`) and two versioned prompt files (`weekly_review`, `job_triage`).

## Files affected
- `apps/mcp-server/src/resources/{profile,job,application}.ts` (new) — MCP resource handlers backing the three URI templates, each a thin read projection reusing 057's underlying queries (no duplicate query logic).
- `apps/mcp-server/src/prompts/weekly_review.md`, `apps/mcp-server/src/prompts/job_triage.md` (new) — versioned prompt files per §4 ("Prompts are versioned files in `apps/mcp-server/src/prompts/`"). Note this is a distinct convention from the `prompts/{task}/{version}.md` LLM-pipeline convention from M5 task 034 — these are MCP-protocol prompts (client-invokable conversation starters), not internal pipeline prompts; keep the two clearly separate, don't conflate them.
- `apps/mcp-server/src/registry.ts` (056/058's file) — register resources/prompts alongside tools.

## Dependencies
- 056 (scaffold), 057 (underlying queries to reuse for resource projections).

## Acceptance criteria
- Resources are genuinely read-only (no resource handler can mutate state — verify by code inspection/test, this should be structurally obvious since resources reuse 057's read-only queries).
- `weekly_review` and `job_triage` prompts render correctly (variable substitution, if any) and reference only tools/resources actually present in the catalog (no hallucinated tool names in the prompt text itself).
- Resource URIs resolve for real ids and return a proper not-found error for nonexistent ones (not a crash/stack trace leak, per §5's "never leak stack traces" rule).

## Test plan
- Integration: resolve each of the 3 resource templates against real seeded data; prompt files load and render.

## Status
DONE.

**Resources are structurally read-only, not just conventionally:** `apps/mcp-server/src/registry.ts`'s `ResourceDef.resolve` signature is `(params, ctx) => Promise<Result<unknown, DomainError>>` — there is no write-capable parameter, and all three resource files (`profile.ts`, `job.ts`, `application.ts`) call into 057's existing read-only queries (`makeGetProfileUseCase`, `makeGetJobUseCase`, and a new `makeGetApplicationUseCase` — the one genuinely new query this task added, a single-item counterpart to `list-applications.ts` that didn't exist yet) rather than any command. `McpRegistry.dispatchResource` requires `read` scope (resources have no per-resource scope in §4, so the whole surface is gated at `read`) and shares the exact same audit-on-every-call posture as tool dispatch.

**`{id}` in `careerpilot://profile/{id}` is accepted but structurally inert (a judgment call inherited from 057):** the profile resource/tool has never supported id-based lookup — `ProfileRepository.findActiveForUser` (the only lookup M3 ever built) always resolves the CALLING TOKEN's own active profile regardless of what `{id}` contains. This was exercised adversarially in `docs/mcp-injection-redteam-checklist.md` §3: supplying another user's real profile id in `{id}` still resolves to "not found" (the caller's own missing profile), never the other user's data — there's no code path that could use the supplied id to look anything up.

**Not-found vs crash (§5's "never leak stack traces," applied to resources):** `job`/`application` resources return `not_found` for a nonexistent or not-owned id via the same `DomainError` -> `McpToolError` mapping tool dispatch uses; `McpRegistry.dispatchResource` additionally catches any thrown exception and maps it to `internal_error` without forwarding the exception's message. Verified with a path-traversal-shaped id (`../../../etc/passwd`) in `injection-redteam.test.ts` payload F — resolves to `not_found`, not a crash or a filesystem read (Drizzle's parameterized queries make this true by construction, not by a special check).

**Prompts (`weekly_review`, `job_triage`) — a genuinely separate convention from M5's LLM-pipeline prompts, kept deliberately distinct:** `apps/mcp-server/src/prompts/*.md` are MCP-PROTOCOL prompts (client-invokable conversation starters a human picks from a menu in Claude Desktop), loaded by a small local loader (`apps/mcp-server/src/prompts/loader.ts`) with simple `{{var}}` substitution — NOT `packages/infrastructure`'s `FilePromptStore` (the `prompts/{task}/{version}.md` convention task 034 established for internal LLM-pipeline templates rendered into a guarded `complete()` call). Both files' text was audited by hand against the real §3 tool catalog (`search_jobs`, `get_job`, `list_applications`, `get_pipeline_analytics`, `match_job`, `update_application_stage`, `add_application_note`) — no hallucinated tool name appears in either prompt; `weekly_review` additionally explicitly instructs the assistant to describe an intended write and get confirmation before calling `update_application_stage`/`add_application_note`, and to never call `prepare_application` speculatively.

**Evidence:**
- Resources are covered by `apps/mcp-server/test/unit/injection-redteam.test.ts` payloads C/F (2 of its 6/6) and exercised end-to-end in the live Docker verification (task 056's Status note — `tools/list`/`initialize` proved the registry boots with resources+prompts registered alongside tools; a full `resources/read` JSON-RPC call was not separately curl'd in this session beyond the tool-level checks, a minor gap relative to a fully exhaustive manual pass, noted honestly here rather than claimed).
