**Test design:** three integration tests, all against real Postgres via genuinely independent
connections (mirroring `budget-lock.test.ts`'s already-proven task 015/016 pattern, one layer up
through the real task 038/039 use-case call sites instead of a raw `guard.complete()` call):
1. **Exact count** (the task's core acceptance criterion): 20 concurrent `score-match` (038)
   requests for the same user. Judgment call: `TieredCostEstimator`'s PRE-dispatch estimate is a
   char-length heuristic over the real rendered prompt — a DIFFERENT number from the fixed-token
   ACTUAL cost a controlled stub response declares. Rather than assume they coincide (they don't —
   first attempt at this test got 0 successes because the conservative estimate rejected every
   call before ever reaching my intended "3 fit" threshold), the test COMPUTES the real estimate
   from the actual rendered `match-score/v1.md` prompt (same facts/job text `score-match.ts` itself
   builds) and derives the exact budget boundary from it, rather than guessing. Result: **exactly**
   3 of 20 succeed, every run — not "usually 3", not "at most 3" — proven by re-running 3 times.
2. **Zero-budget tailoring** (039): 8 concurrent `tailor-document` requests against a literal $0
   budget — every single one rejected with `budget_exceeded`, zero `ai_invocations` rows, zero
   calls ever reached the stub "provider" (`dispatchCount === 0`) — the guard rejects before
   dispatch, not after a failed call.
3. **Mixed concurrent fan-out** (the task's literal ask: "concurrent fan-out of matching (038) +
   tailoring (039) requests via `Promise.all`"): 16 requests, alternating kind, one shared low
   budget. Asserts (a) total recorded spend never exceeds budget, (b) at least one request of
   EACH kind was rejected (proving the hard stop actually engaged for both call sites, not just
   one), and self-consistency between the dispatch counter and the `ai_invocations` row count
   (every recorded row corresponds to exactly one real dispatch, never more).
