# 063 — Wire the production mapping/filling trigger + CareerProfile contact fields

**Status:** TODO | **Milestone:** M6 (follow-up, found during the M6+M7 merge verification)

## Objective
Close a real gap found during independent post-merge verification, not previously flagged by either milestone's own Status notes: **there is no production entry point that drives a freshly-created `ApplyTask` from `draft` through `mapping`/`filling` to `awaiting_review`.** `POST /apply-tasks` (`apps/api/src/routes/apply.ts`) only calls `makeStartApplyTaskUseCase`, which creates the task in `draft` and stops. `makeRunMappingUseCase`/`runFillStage` are real, tested, and correctly implemented (proven by task 054's e2e spec and the unit/integration suites) — but the ONLY place they are ever invoked outside of tests is that one e2e spec, which calls them directly in-process. `apps/browser-runner/src/task-api.ts` has `/internal/tasks/:id/submit` and `GET /internal/tasks/:id/fields`, but no route to start mapping. `PlaywrightFieldDetectionAdapter`'s own doc comment even references "task-api.ts's mapping trigger" as the intended caller — that trigger doesn't exist.

A second, related gap `fill-runner.ts`'s own doc comment already names honestly: `CareerProfile` (M3) has no first-class contact-info fields (name/email/phone) — `FillRunnerInput.valuesByKey` is supplied by "the CALLER (task-api.ts's mapping/filling trigger)", which doesn't exist yet, and even once it does, there is currently no source of truth in the domain model to resolve those values from.

Net effect: today, a real user creating an ApplyTask via the real API/UI has it sit in `draft` forever. This is not a safety gap (nothing unsafe is reachable) — it's a completeness gap. Flagging it explicitly rather than letting M6 read as "fully wired end-to-end" when it isn't yet.

## Files affected
- `packages/domain/src/profile/profile-section.ts` or a new top-level `CareerProfile` field — add minimal contact fields (`firstName`, `lastName`, `email`, `phone` at minimum — check `TAXONOMY` in `packages/domain/src/apply/field-taxonomy.ts` for the exact P0 field set fill-runner needs). Migration required (`packages/infrastructure/src/db/migrations/0010_profile_contact.sql` or similar — note migration numbering already has a `0007` collision between M6's `apply_tasks` and M7's `mcp_tokens`; use the next real available number, currently 0010).
- `apps/browser-runner/src/task-api.ts` — new `POST /internal/tasks/:id/start` (or similar): opens the browser context at the job posting's `url` (`ApplyTaskBrowserContextManager.open`), calls `makeRunMappingUseCase`, resolves `valuesByKey` from the CareerProfile's new contact fields, and — if `!manualAssistRequired` — calls `runFillStage`. On `manualAssistRequired`, leave the task in `mapping` per task 055's existing "never dead-ends" behavior (already correctly implemented, just needs a caller).
- `apps/api/src/routes/apply.ts` / `apps/api/src/lib/browser-runner-client.ts` — a new `BrowserRunnerStartPort`-shaped HTTP client (same pattern as `HttpBrowserSubmitClient`/`HttpBrowserRunnerFieldsClient`), called by `POST /apply-tasks` right after `startApplyTask` succeeds (or as an explicit separate `POST /apply-tasks/:id/start` the web UI calls next — either is fine, pick whichever matches how task 052's review-queue UI is already structured, and document the choice).
- `apps/web/src/app/apply/copy-paste-assist/page.tsx` — once the trigger exists and copy-paste-assist is a real reachable outcome (not just unit-tested), this page's own documented gap ("no dedicated `GET /apply-tasks/:id/copy-paste-values` endpoint yet") should also be closed, reusing the resolved contact-field values from this task.

## Acceptance criteria
- `POST /apply-tasks` (or a documented follow-up call) results in a real ApplyTask reaching `awaiting_review` (or the `manualAssistRequired` copy-paste-assist path) without any test-only direct in-process command invocation — i.e., the same real HTTP-only path task 054's e2e spec deliberately did NOT exercise (see that task's Status note's own documented scope decision) needs its own black-box `docker compose up` + HTTP-only e2e test.
- `CareerProfile`'s new contact fields round-trip through the existing profile CRUD routes/UI (task 022/025) without breaking any M3-era profile test.
- Sensitive-field policy (never-auto-fill) is unaffected — contact fields are ordinary (non-sensitive) taxonomy fields, no change to that invariant.
