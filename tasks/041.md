# 041 — Diff-review UI (web)

**Status:** DONE | **Milestone:** M5

## Objective
Implement the M5 roadmap acceptance criterion "diff-review UI functional" and the docs/06-agent-design.md §4 point 4 requirement: "Human review is non-skippable before export/use. The UI shows a semantic diff against the base document and the claim→fact mapping." This is the user-facing gate that makes 040's `needs_human` flag meaningful rather than a dead-end state.

## Files affected
- `apps/web/src/app/` — new route for reviewing a generated `DocumentVersion` (follow the existing routing/page conventions from task 025's profile editor / document history UI — check `apps/web/src/app` structure before inventing a new pattern).
- `apps/web/src/components/` — a semantic diff view (base document content vs. generated version — reuse `@careerpilot/ui` components from task 018 where they fit; a plain structural diff over the `ResumeDocumentContent`/`CoverLetterDocumentContent` JSON, rendered as added/changed/unchanged per bullet, is sufficient — do not pull in a heavyweight text-diff library for a two-line change if the repo doesn't already have one).
- `apps/web/src/components/` — claim→fact mapping panel: for each flagged/unsupported claim from 040's `ClaimAudit`, show the claim text and either its mapped fact or an "UNSUPPORTED — needs your review" state, with an accept/reject action per claim.
- `apps/api/src/routes/documents.ts` (extend) — endpoints the UI needs: fetch a version's `ClaimAudit` + diff data, submit human review decisions (accept-as-is / edit / reject-and-regenerate), which then clears `needs_human` and unblocks export (per 040's export-blocking gate).
- `packages/contracts/src/documents.ts` (extend) — DTOs for the review payload.
- Tests: component tests if the repo has a component-testing setup already (check `apps/web` for existing test infra from task 025 before adding a new one), API integration test for the review-submission → `needs_human` cleared → export unblocked flow.

## Dependencies
- 039, 040 (needs real tailored documents with claim audits to review).

## Acceptance criteria
- A `needs_human: true` document version cannot be exported from the UI (button disabled/hidden with a clear explanation) until review is submitted.
- Reviewer sees, per flagged claim: the claim text, the semantic diff context it appears in, and either its fact mapping or its UNSUPPORTED status.
- Submitting a review (accept/reject per claim) updates the document version's review state and — for accepted-as-clean reviews — unblocks export.

## Test plan
- API integration: full round-trip — tailor (039) → verify (040, force an UNSUPPORTED fixture) → fetch review payload → submit review → assert export is now permitted.
- Manual browser verification (per this project's standing rule for UI changes): start the dev stack, walk the golden path (generate → review → export) and the edge case (reject a claim, confirm export stays blocked) in an actual browser before marking DONE.

## Status
DONE.

**API extension:** `GET /documents/:id` (existing, task 022) now carries `needsHumanReview`/
`flaggedClaims` per version (task 040's fields, threaded through `get-document.ts`) — this alone
supplies both "the claim audit" and "the diff data" the review UI needs, so no separate fetch
endpoint was added. New `POST /documents/:id/versions/:versionId/review` (`{approved: boolean}`)
resolves a pending review via the new domain method `Document.resolveReview` /
`DocumentVersion.withReviewResolved` (additive — `approved:true` clears `needsHumanReview` and
unblocks export via the existing `render-document.ts` gate from task 040; `approved:false` is a
real, recorded outcome, not a no-op — it leaves the version blocked).

**UI:** `apps/web/src/components/DocumentDiffView.tsx` (plain structural added/removed/unchanged
diff over the resume/cover-letter JSON — no diff library, per the task's own scope note) and
`ClaimReviewPanel.tsx` (per-claim accept/reject, single submit gated on every claim having a
decision) — new `apps/web/src/components/` directory (didn't exist before this task).
`apps/web/src/app/documents/[id]/review/[versionId]/` is the new dedicated route (Next 15 server
component unwrapping the dynamic segments, handing off to a 'use client' `ReviewClient`). The
existing `/documents` list page now shows a "needs review" badge + review link INSTEAD of
render/download buttons for a flagged version — the export-blocking gate surfaced in the UI, not
just the API.

**Judgment call — added a minimal "Tailor with AI" trigger to `/documents`:** task 039's file list
never touched `apps/web` (API/worker only), so there was no way to reach the generate -> review
flow from the browser at all. Task 041's own manual-verification instruction ("walk the golden
path: generate -> review -> export") needs one. Added the smallest possible form (paste a job
posting id, POST `/documents/:id/tailor`, poll after 8s) rather than leaving this task's own
acceptance criterion unreachable.

**REAL BUG FOUND AND FIXED during manual verification:** `apps/api/Dockerfile` ran the API as the
non-root `careerpilot` user without ever chown'ing `/app/apps/api` (owned by root from the build's
COPY layer) — `LocalFileObjectStorage`'s lazy `mkdir` of `./data/documents` (task 024) failed with
`EACCES` on the FIRST real render/export ever attempted through the actual Docker image (task
024's own tests always ran against a host temp dir, never inside the container). Found via the
literal export step of this task's browser walkthrough — not a task 041 regression, but it
directly blocked verifying task 041's central claim ("approve unblocks export" must mean export
actually *works*, not just that the 409 goes away), so fixed it in place: pre-create and chown
`data/documents` before the `USER careerpilot` switch. Verified fixed by re-running the exact same
export call after a full `docker compose up -d --build`.
