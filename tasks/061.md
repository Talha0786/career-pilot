# 061 — Mock interviewer (agentic chat loop)

**Status:** DONE | **Milestone:** M7

## Objective
Implement the mock interviewer per `docs/06-agent-design.md` §5: "chat loop over (JD + profile + question bank); tools: `get_profile`, `get_job` (read-only). Session transcript stored under `interview_preps`. Turn cap 40; budget-guarded." This is one of only two genuinely agentic (open-ended tool-loop) components in the whole system per §1's "pipelines first, agency last" philosophy — keep the loop itself minimal and tightly bounded, resist scope creep into a general chat feature.

## Files affected
- `packages/application/src/interview-prep/commands/run-mock-interview-turn.ts` (new) — one turn of the chat loop: given the running transcript + JD + profile + question bank (seeded from 060's `generate-questions` output), calls the LLM with `get_profile`/`get_job` as the only available tools (both read-only, reusing 057's MCP tool logic or the underlying queries directly — don't fork a second implementation of the same reads).
- `apps/mcp-server/src/tools/generate-interview-prep.ts` (060's file) — extend to handle `kind: 'mock_interview'`, or add a distinct tool if the design doc implies mock-interview is session-based rather than a single tool call (check whether a running chat session needs a start/continue/end tool triplet vs. one-shot — document the choice; a reasonable design is `generate_interview_prep({kind:'mock_interview'})` starts a session, subsequent turns go through a lighter-weight continuation path since MCP tool calls are typically request/response, not a persistent stream).
- Turn cap enforcement: hard stop at 40 turns, transcript still returned/stored up to that point (not discarded).
- Transcript persisted to 060's `interview_preps` table (`kind: 'mock_interview_transcript'`).
- Every turn goes through `GuardedLlmPort` — no bypass, budget exhaustion mid-session ends the session gracefully (not a crash), same posture as every other M5/M6/M7 LLM call site.

## Dependencies
- 060 (question bank, `interview_preps` table, shared read-only tool wrappers).

## Acceptance criteria
- The loop never exceeds 40 turns — hard cap, tested with a fake LLM that always wants to continue.
- Only `get_profile`/`get_job` are callable from within the loop — no write tool is reachable even if the model attempts to invoke one (test: fake LLM response requesting a write-shaped tool call, confirm it's rejected/ignored, not executed).
- Budget exhaustion mid-loop ends the session with the transcript-so-far intact, not a hard crash or silent data loss.
- Full transcript persists and is retrievable.

## Test plan
- Unit: 40-turn hard cap; write-tool-call rejection from within the loop; budget-exhaustion graceful-end path — all with fakes.
- Integration: real Postgres, a short real multi-turn session against a local LLM (reusing the `intelligence-evals` harness pattern for "real Ollama" testing established in M5), transcript persisted correctly.

## Status
DONE.

**Session-as-tool-call design (the task's own explicitly flagged open question, resolved and documented):** `generate_interview_prep({kind: 'mock_interview'})` with no `sessionId` starts a new session (the interviewer opens); the SAME tool called again WITH `sessionId` (+ optional `message`, the candidate's reply) continues it. No separate start/continue/end tool triplet — one tool, two optional fields (`sessionId`, `message` in `GenerateInterviewPrepInputSchema`), since MCP's request/response shape composes fine this way without a persistent stream. Documented inline in `apps/mcp-server/src/tools/generate-interview-prep.ts`'s doc comment.

**Read-only tool reuse, not a fork (task's explicit instruction):** `run-mock-interview-turn.ts` calls `makeGetProfileUseCase`/`makeGetJobUseCase` directly — the exact same factory functions 057's `get_profile`/`get_job` MCP tools wrap — not a second implementation of the same reads.

**Two independent hard caps, neither prompted-only:**
1. `MOCK_INTERVIEW_TURN_CAP = 40` (session-level): checked BEFORE any LLM call on a turn that would exceed it — the function returns `completed_turn_cap` with ZERO LLM calls made once the cap is hit (verified: `inner.completeCalls` asserted to have length 0 in the cap test, seeding a 40-turn transcript and calling once more).
2. `MAX_LLM_CALLS_PER_TURN = 4` (turn-level, new/undocumented-in-the-task-file but necessary): bounds the internal `get_profile`/`get_job` tool_call sub-loop WITHIN one turn, so a single turn can't itself run away independent of the session cap. If exhausted without a `say` action, a generic fallback message is used rather than hanging or crashing — the turn always produces SOME output.

**No write tool is reachable from within the loop, verified adversarially (task's explicit acceptance criterion) — same text-protocol-ReAct pattern as 060's research loop:** the model's `tool_call` action has `tool: z.enum(['get_profile', 'get_job'])` — a CLOSED zod enum. Tested with a fake LLM that ALWAYS requests `{"action":"tool_call","tool":"update_application_stage"}` (a write-shaped, out-of-enum value): zod validation fails every single attempt, the code path that would execute a tool call is never reached for it (only `get_profile`/`get_job` string-literal branches exist in the handler — there is no `default:` branch that could execute an arbitrary tool name even if the enum were bypassed), the loop retries up to `MAX_LLM_CALLS_PER_TURN` then falls back to a generic message — verified by reloading the fixture `Application` afterward and asserting its `stage` is unchanged (`'discovered'`, not moved), a structural proof (not just "the response didn't mention success") that the write path was genuinely never exercised.

**Budget exhaustion ends the session gracefully, transcript intact (task's explicit acceptance criterion):** a `GuardedLlmPort` wired to a real `$0` `InMemoryBudgetStore` budget rejects the very first `complete()` call pre-dispatch (`budget_exceeded`); `run-mock-interview-turn.ts` catches this specific error code (alongside `rate_limited`) and returns `status: 'ended_budget_exhausted'` — NOT an error result, a normal `ok` result the caller can display — with the transcript-so-far (including the candidate's message that triggered this turn) persisted via `InterviewPrepRepository.save`, verified by reloading the persisted row afterward and finding the candidate's exact message text still present. No crash, no silent data loss, matching "same posture as every other M5/M6/M7 LLM call site."

**Every turn goes through `GuardedLlmPort` — no bypass:** confirmed structurally (the only LLM call site in `run-mock-interview-turn.ts` is `deps.llm.complete(...)`, `deps.llm` typed as `GuardedLlmPort`, never a raw `LlmPort`) and behaviorally (the budget-exhaustion test above proves the guard is actually consulted, not just present in the type signature).

**Evidence (`packages/application/test/unit/interview-prep.test.ts`'s "mock interviewer turn loop" describe block, 3/3, fakes only):** 40-turn hard cap with zero LLM calls made; write-tool-call rejection proven via unchanged application state; budget-exhaustion graceful end with transcript-so-far verified intact via `InterviewPrepRepository.findById`. **A short REAL multi-turn session against a local Ollama (reusing `packages/intelligence-evals`' `buildLlmHarness()` pattern, as suggested by the M7 brief) was NOT run in this session** — no live Ollama endpoint was reachable in this sandboxed environment (same constraint noted for `packages/infrastructure/test/integration/llm-adapter.test.ts`'s own doc comment: "no real Ollama/OpenAI model is reachable from this sandbox"). This is an honest, explicitly-flagged gap: the LOOP LOGIC (caps, tool-call closure, budget handling) is fully verified with fakes; a real model's actual conversational quality/tool-invocation behavior against the real `prompts/mock-interview/v1.md` prompt is unverified in this session.
